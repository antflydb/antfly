# PDF render regression verification (internal)

Internal engineering measurements using the curated Circus/OHR-Bench corpus.
Observe the research/non-commercial restriction described in [README.md](README.md).
These are local source-build measurements, not a release-package benchmark,
an OCR accuracy evaluation, or marketing results.

## Subjects and method

- Baseline: `origin/main` pinned to `98d911a88cff9fd29fd9cc3b78c22ebb78b20df5`.
- Original candidate: `0c5973d3ebc80e1834d920eee4dbb8c8f3aa41d1`.
- Final fixed candidate: `61a08302ff07e94f1292a6e5d9cd998f1ea8a25e`.
- Apple M4 Max, 36 GiB RAM; Zig 0.16.0, ReleaseFast, Metal enabled, ONNX disabled.
- Same Florence-2-base and BGE-small safetensors files, hashed per process.
- Antfly fetches original PDFs over loopback HTTP, extracts/OCRs, chunks,
  embeds, and publishes searchable vectors. Timing includes ingestion through
  converged artifact/index coverage; startup and table setup are separate.
- Mixed `text` suite: three PDFs, nine pages. `auto` and forced `always` OCR
  are separate experiments. Paired runs alternate process order; each trial
  uses a fresh table. Filesystem caches and other host activity are uncontrolled.
- A timing comparison requires exact retained page-text hashes, page/DPI
  metadata, render-quality warnings, per-document artifact/OCR counts, and
  published vector counts.
  Unknown rotation remains null and is compared as such; OCR DPI and rendered
  dimensions must be present. This does not establish OCR correctness.

Raw artifacts live under the ignored `.benchmark-results/pdf-verification/`
directory of this worktree. Each run retains configuration, commands, binary
and model hashes, server logs, source-fetch logs, manifests, and output checks.

## Original regression

The earlier forced-OCR comparison took 9.772 s on main versus 36.910 s on the
original candidate (median of per-process warm-trial medians). Outputs differed,
so these are diagnostic elapsed times, not an equivalent-work throughput ratio.

A separate profile attributed about 92% of that elapsed-time delta to the
newspaper render window: main 1.181 s, original candidate 21.959 s including
replay after scratch exhaustion. Worker allocation incurred repeated system
mappings and delayed freed-slot reuse. The candidate also rendered at lower
DPI automatically: newspaper 39 versus 138, textbook 44 versus 150.

## Fixes and regression checks

Requested DPI is now the default policy; model-input-sized rendering is opt-in.
Window and worker counts shrink under resource pressure, without silently
changing geometry. Render workers use private reusable size-class heaps, with
all backing memory charged. Scratch growth is non-blocking and capped; replay
preserves successful pages and retries failed identities only. Measured scratch
hints affect admission, not quality. Transform identities are versioned.

The first rebuilt candidate exposed a second admission defect: the extraction
slice shares its 256 MiB cap between scratch and retained output. The planner
could reject a valid partial scratch grant against its conservative estimate.
OCR and embedding now use the same wave planner before and after admission,
allowing one worker to attempt the actual hard-bounded grant.

A further pixel comparison exposed allocation-dependent materialization work:
the serial renderer uses moving `realloc`, whereas failed heap remaps caused
replacement allocations to be charged again. The bounded heap now implements
moving remaps, retaining both allocations' physical charges during the copy.
The newspaper's 4,935 text groups then render without fallback; exact pixels
and all recorded renderer diagnostics match the serial reference. Cumulative
materialization is 526,889,196 bytes on both, under the unchanged 512 MiB work
ceiling. This is separate from the live scratch-memory ceiling.

Development-only renderer diagnostics (excluded from end-to-end aggregates):

| Page | Effective DPI | Render time | Measured worker scratch |
| --- | ---: | ---: | ---: |
| Newspaper (final, exact pixel parity) | 138 | 904 ms | 176,914,432 bytes |
| Textbook | 150 | 72 ms | 28,655,616 bytes |

The newspaper uses the actual 211,250,964-byte production scratch grant, below
the unchanged 268,435,456-byte configured ceiling. The textbook diagnostic uses
that configured ceiling. The textbook's
conservative admitted estimate was 243,900,456 bytes, illustrating why estimates
must not become additional hard quality limits. These are not peak process-RSS
measurements. Earlier newspaper figures of 796 ms and 125,075,456 scratch bytes
were collected before moving-remap support and used degraded rendering; they
are not quality-qualified performance evidence.

Validation: 460 PDF tests in both Debug and ReleaseFast; native integration
including a partial resource-manager grant at unchanged 150 DPI; targeted
planner and retry-ownership tests with zero leaks; Python harness tests and lint.

## End-to-end results

The final Metal build completed. Both experiments below used two alternating
pairs of fresh processes and three trials per process (12 trials per mode).
All exact text, geometry, render-quality-warning and structural gates passed.
Warm times are the median of per-process medians of trials 1 and 2, not a
pooled median. Reader microbatch capacity was pinned to four on both subjects.

| Mode | Main first trial | PR first trial | Main warm | PR warm | Warm elapsed change | Warm throughput ratio |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Forced OCR (`always`) | 8.444 s | 6.693 s | 8.518 s | 6.604 s | -22.5% | 1.290x |
| Embedded text + OCR fallback (`auto`) | 3.864 s | 3.612 s | 3.686 s | 3.395 s | -7.9% | 1.086x |

Artifacts: `quality-final-main-pr-text-always-b4-20260908` and
`quality-final-main-pr-text-auto-20260908`. Forced-OCR warm paired throughput
ratios were 1.267x and 1.313x; auto ratios were 1.098x and 1.074x. Other host
activity remained uncontrolled (forced-OCR one-minute load 6.61–8.30). These
are load-qualified local engineering observations, not confidence intervals or
a general performance guarantee. The comparison is against pinned main, not rc.5.

The additional four-PDF/ten-page `small` auto probe
(`quality-final-main-pr-small-auto-b4-20260908`, one pair, one trial) failed on
main: the required-OCR administration scan had no chunks, OCR was not selected,
and vector coverage was incomplete. The PR passed its structural checks. Keep
this failed comparison; it supplies no equivalent-work speedup or OCR accuracy
claim and must not be pooled with the successful `text` experiments.

### Batch-size diagnostics and remaining headroom

Capacity one and two each used one pair and three trials per process. Both
passed exact output parity. Main/PR warm times were 9.007/7.790 s at one and
8.536/7.350 s at two. Alongside the capacity-four result above, this is
directional evidence of useful batching, not a randomized capacity study.
Batch-size experiments have different host activity and must not be pooled.

Capacity eight (`quality-final-main-pr-text-always-b8-20260908`) completed all
six structural checks but failed exact text parity on academic pages 4 and 5
in every trial. Geometry, render-quality warnings, newspaper and textbook text
match. Its diagnostic warm times were main 8.370 s / PR 6.961 s; the comparison
driver correctly reports no qualified timing ratio. At this capacity the outer
page grouping differs (main four-plus-three, PR seven). Establish batch-shape
numerical/output correctness before attributing the text changes to harmless
floating-point variation; they are not evidence of equivalent OCR quality.

Main already performs native Florence batching; this is not a serial-to-batched
comparison. Nine pages across three sources also leave small tail batches and
do not exercise shared rendering across multiple consumers, remote inference
transport, or a sustained cross-request queue. Auto mode bypasses OCR on most
pages. The general scheduling infrastructure cannot accelerate work absent from
the workload.

Separate final-build profile `quality-final-stage-profile-b4-20260908` passed
structural gates and retained the capacity-four text/geometry. Its 7.423 s
elapsed time is diagnostic only, excluded from the paired timing aggregates.
The four OCR calls (4, 3, 1, 1 pages) took 1.652, 2.289, 0.530 and 0.523 s:
4.993 s in total. Vision stages across them took 2.083 s. The second academic
batch alone took 1.563 s in decoder execution. The newspaper render took
0.938 s. Profile intervals are nested and prefetch overlaps rendering with OCR;
do not sum all phase durations as independent critical-path costs. In particular,
the second academic render-window interval includes time before consuming the
prefetched result, not just CPU rasterization.

Priorities for the next optimization iteration:

1. Measure steady-state utilization with the larger corpus, concurrent sources,
   and multiple compatible consumers. Record actual batch occupancy, model queue
   wait, admission wait, rendering and inference service time separately. Compare
   matched shapes against main and sweep capacities within each subject on a
   quiet host. Nine-page single-consumer latency is not a saturation benchmark.
2. Resolve the capacity-eight output divergence with identical rendered tensors
   through singleton and batched encoder/decoder execution. Keep exact parity as
   the regression check; any intentional numerical change also needs a separate
   OCR accuracy evaluation before a default change.
3. Profile and optimize the dominant Metal vision/decoder kernels and per-token
   synchronization, preserving cancellation and hard resource bounds. KV caching
   and completed-row compaction already exist; adding another scheduler or cache
   does not remove this compute. Backend primitives should remain reusable across
   model families, with model-specific correctness tests.
4. Extend device-resident vision-tail support by backend capability and batch
   shape. Today Florence permits it only for CUDA at batch one; Metal/batched
   work takes the CPU-tail fallback. However the measured download, positional
   embedding, feature-source assembly, projection and normalization intervals
   total only about 38 ms here. Useful cleanup, but not the main performance win.
5. Use measured render working-set hints to improve safe concurrency and batching
   under fixed grants. Preserve the existing one-window prefetch and shared-window
   ownership model; increasing worker counts or reducing DPI is not an equivalent-
   quality optimization. The large newspaper still needs about 169 MiB of scratch
   plus retained pixels, so it cannot share an arbitrary full render batch within
   the current 256 MiB slice.

For scale intuition only, halving the measured 4.993 s OCR service time with all
other cost unchanged would move the diagnostic 7.423 s toward 4.927 s (about
1.51x). This is an optimistic cost model, not a prediction: overlap, admission,
batch shape and synchronization can change the critical path.

Intermediate candidate `a14daff8d` completed `quality-v2-main-pr-text-auto-20260908`
with exact output parity. Warm times were main 4.260 s / PR 7.792 s; substantial
overlapping host work included an unrelated Antfly VectorDBBench process.
The intermediate forced-OCR experiments completed all trials, but their output
gates failed. With the default reader capacity, two academic pages and the
newspaper differed. At capacity four, only the newspaper differed. Its render
materialization fallback led to the final moving-remap fix above. Keep these
experiments in the record; neither is a qualified forced-OCR speedup.

The preliminary `quality-main-pr-text-auto-20260908` experiment was interrupted
after the admission/metadata failures were recorded. Preserve it, along with
