# Gemma4 E4B QAT Q4_0 text qualification — GB10, 2026-10-31

One NVIDIA GB10, one stream, two CPU threads/cores, F16 KV, cache disabled, greedy decoding, one warmup and five measurements per workload. The primary native run uses the release 2048-token graph-capacity profile.

Enable the [GB10 profile](../gemma4_e4b_qat_gb10.env) before starting a dedicated inference server. Keep input plus requested output within its 2048-token capacity. The BF16 prefill mirrors add about 7.4 GiB of resident device memory; existing admission limits still apply.

A separate llama.cpp 512-token block followed all native measurements. The native/reverse-llama decode ratio was 1.0170× [1.0142, 1.0185]. The adaptive-capacity campaign 02 is supplemental evidence in JSON.

Decode is a visible-content-based SSE proxy: `(completion_tokens−1)/(terminal usage−first visible content)`. Chunk sizes do not establish alignment. E2E includes TTFT and completion overhead; read the latency columns separately. The short 256-token request is about 0.5% slower end to end than llama.cpp, with roughly twice the first-token latency. The 512-token and long-prompt requests are faster end to end. Native does not establish an across-the-board latency advantage.

All engines received identical prompt token IDs and the same learned GGUF bytes. Native candidate/control text, counts and finish reasons match. Runtime precision differs: native uses F32 hidden state with selected Q8 dot paths/BF16 prefill mirrors; vLLM uses F16 activations. This is timing evidence for three fixed workloads, not cross-engine quality certification or a global-fastest result. Five-sample intervals describe each block; they do not estimate session-to-session variance.

vLLM 0.29.0 retains stock O2/Inductor/CUDA-graph defaults and Triton attention. Its recorded GGUF loader compatibility patch preserves learned weights and fills only unused shared-cache K/V slots. Manifest SHA-256: `a5109eddf0e45b80f268cd294b17dd6ad90ea6e0d8085de7f2d8960f959d398f`.
