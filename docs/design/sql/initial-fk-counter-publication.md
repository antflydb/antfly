# Atomic initial foreign keys and column counters

Initial FK creation uses the existing hidden-child publication protocol. Column
counters belong to that protocol's immutable catalog postimage; they do not
require a second CREATE, an ALTER replay, or another coordinator.

The metadata preparation read assigns the child identity and derives counter
bindings from the current namespace and allocator cut through the ordinary
column-sequence factory. The result contains the bound child schema and bounded
counter effects. Admission independently repeats that derivation under the
catalog revision CAS and compares the complete postimage. Proposed IDs, names,
configuration and ownership therefore carry no authority by themselves.

Admission advances the monotonic allocator past the child slot and every new
counter ID. It reserves counter names in the same canonical namespace registry
as the hidden table and its indexes. A reservation has its own sequence kind,
child identity and publication ID. Neither a counter resource, a running counter,
a column registry nor a default dependency becomes public at this stage.

Owners provision the empty hidden child from the already bound schema. Existing
parent generation preparation, activation, readiness and child-release receipts
remain the only path to publication. Final publication verifies each counter's
exact reservation and absence, prepares the child with a sealed counter overlay,
and commits these effects in one metadata transaction:

- The table and range/catalog bindings.
- Attribute identities and default-reference edges.
- Counter catalog records, initial states and ownership edges.
- Terminal publication and reservation cleanup.

The overlay validates defaults before the counter records exist; it is built
only from the immutable, independently verified postimage. Counter configuration
is never recomputed from a later namespace cut. Counter values are not allocated
while the child is hidden. A stale publication command cannot initialize or
reset an already published counter.

Cancellation uses existing owner cancellation and retirement receipts. Since
counter resources were never published, cancellation releases reservations
without deleting a visible counter or repairing a default afterward. Reserved
allocator IDs remain consumed, preventing delayed work from targeting a later
same-name creation. The immutable postimage and existing work indexes survive
cold recovery; SQL is not replayed.

Sequence references have one canonical JSON codec for both schema references
and typed durable envelopes. IDs are decimal strings and the incarnation is a
fixed hex string. The typed parser validates that same representation and owns
its diagnostic strings in the caller's region. Stream and value parsing must
round-trip exact u64 values and clean up every failed allocation.

Metadata decoder cohort 128 fences counter effects and sequence-name
reservations, including pending and retained initial-publication records in
snapshots. Empty legacy fields remain omitted. No new public route, standalone
counter publication, or public schema enum is introduced.

## Qualification contracts

`system-catalog-sequence-binding-test` checks typed stream/value round trips,
exact IDs, UTF-8 and exhaustive allocation-failure ownership. It also runs under
the combined SQL gate.

`antfly-metadata-initial-counter-test` selects the native publication and
cancellation campaigns with zero skips permitted. The publication campaign
checks old-decoder nonadmission, forged postimages, hidden counter/name state,
cold metadata recovery, real native owner preparation/release, final counter
state and ownership, and aborted publication preparation under allocation
failures. The cancellation campaign cold-reopens admitted work, applies real
owner cancellation, checks absent counters and released names, and prepares a
fresh identity using those names. The broader initial-FK gate retains ordinary,
self, multi-range, support-index and hosted-root regressions.

`antfly-api-sql-definition-copy-test` exercises combined public CREATE with
identity, SERIAL, generated columns, deferred UNIQUE, CHECK and an external FK.
It retains the original receipt through bounded observation, then checks actual
allocation, LIKE copying, cold owners and coupled borrower/source retirement.
The independent PostgreSQL visibility witness is generated by
`scripts/generate_sql_initial_counter_reference.py`; the unchanged persistence
oracle remains separate evidence for the original LIKE statement.

Copied counter defaults now use a [shared live-source dependency
lease](initial-fk-counter-dependencies.md) through the hidden interval, with
independently rederived source bindings and definitions. Self-contained LIKE
definitions and column/object notes use the [guarded copy
postimage](initial-fk-definition-copy.md) in the same initial publication.
Owning-table CASCADE and role-owned initial publication retain their separate
admission requirements. These limits do not permit weakening the explicit-counter
publication or its fault tests.

On 2026-10-31 the combined pinned-Zig Debug gate passed the 21-test initial-FK
suite, both strict counter campaigns, both mounted campaigns, the binding codec
and all 1,904 SQL tests. Only the four existing opt-in SQL benchmarks skipped;
there were no failures or leaks. The allocation-failure campaign preserves the
complete metadata snapshot and emits no projection signals before commit. An
already allocated counter retains its value/revision after a duplicate final
publication. The PostgreSQL 18.6 visibility/cancellation witness passed too. No
additional immutable original is counted merely for these auxiliary combinations.
