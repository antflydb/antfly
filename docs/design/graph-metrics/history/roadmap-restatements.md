The log has two parts. Phases 0-7 describe the graph metric framework (PageRank first, then degree, eigenvector, and HITS), each with a "current implementation progress" block. The rest restates the remaining distributed/resumable execution roadmap about eight times as work landed. The log has no per-entry dates. By its end, a durable planned executor (jobs, manifests, page leases, attempts, barriers, verified publish, cleanup) was running for all four metric families. It was exercised through local runners, DB-level sweeps, an in-process runtime, spawned processes, and real HTTP service-targeted owners. Distributed-by-default promotion was still blocked on deployment-scale owner, fan-in, cleanup/storage, and latency evidence.

## Framework phases (as designed)

| Phase | Outcome |
| --- | --- |
| 0. Framework baseline | Durable dirty and published-generation metadata, local PageRank, fixed-iteration publish with `converged: false`, NaN/infinity rejection, and states `not_ready`/`fresh`/`stale`/`building`/`failed`. Restart coverage proves dirty state and the last published generation survive reopen, and a failed rebuild keeps serving the prior generation. |
| 1. Query integration | Metric projection, ordering, and filtering on graph traversal/search nodes, plus optional `metric_status`. `metric_freshness` is threaded through local and remote reads. A public HTTP e2e covers not-ready, fresh, stale (after a `sync_level: "write"` update), building, and failed states. |
| 2. Distributed jobs | Durable per-metric build job record, per-job manifest, deterministic pages, page leases with attempts, cursors, phase summaries and barriers, iteration/convergence summaries, a verified-publish gate, and bounded failure diagnostics. |
| 3. More metrics | `degree`, `eigenvector` (fixed-iteration power iteration), and `hits_authority`/`hits_hub` (one computation, atomic paired publish). Personalized PageRank is deferred. |
| 4. Edge scope | The resolved edge filter and a config fingerprint are stored per published generation. A fingerprint mismatch reports `stale`. Edge-scope validation rejects empty typed scopes, blank or duplicate types, `all` combined with types, and unknown types when type metadata exists. |
| 5. Operations | `POST /tables/{table}/indexes/{index}/graph-metrics/{metric}:{action}` for `refresh`, `rebuild`, `delete`, `pause`, `resume`, all idempotent and returning status. `delete` writes a durable disabled marker. Durable events with bounded `recent_events`, `retry_count`/`last_error`, and build-lease status fields (`build_job_id`, `build_started_at_ms`, phase, iteration, worker). |
| 6. Retrieval composition | `graph_metrics` profile entries, explicit `graph_metric_rerank`, and a fail-closed cross-shard gate (see Decisions). |
| 7. Compatibility | Metadata schema version `3` (`metadata_version` is optional in clients). Empty and duplicate metric names are rejected. |

## Decisions

### Public contract (frozen early, restated in every roadmap revision)
- Metrics live on the graph index under stable, user-provided names. There is no job-submission API, and jobs, pages, attempts, leases, worker ids, retry policy, and cleanup queues stay internal. Status may summarize them. Reason: stability. Churn here would multiply generated-client and query-path work.
- `published` is the default freshness. It returns the latest complete generation even while a rebuild is queued, building, or failed. `fresh` fails with `MetricNotReady` before the first publish and with `MetricStale` once newer graph writes exist.
- Fixed-iteration non-converged PageRank, eigenvector, and compatible HITS publish by default, with `converged: false`, `iterations_completed`, and final deltas.
- Projection returns `null` for a missing generation or node score. Ordering defaults to `nulls_last`, and ties break by the graph query's existing deterministic node order, then key. Filtering comes after ordering and fails closed.
- Metric families must be named explicitly. Names like `pagerank_mentions_cites` are not generated from filters, because stable names matter for query APIs, status, retention, and migrations.
- A change to an edge filter or to any algorithm-affecting setting (kind, damping, tolerance, max-iterations, edge scope) creates a new materialization, and status reports `stale`.
- Retention is latest-only by default. Cleanup runs immediately when reads are snapshot-safe and otherwise goes through a deferred internal queue. Future retention is an opt-in, bounded admin/debug option and never part of query semantics.
- Migration must never recompute scores synchronously at startup. It marks the metric stale or not ready and lets maintenance rebuild asynchronously.
- Score blending is explicit only: `graph_metric_rerank` computes `final_score = base_weight * existing_score + weight * metric_score`, with `missing_score` as the fallback, and attaches per-hit `_score_details.graph_metric_rerank`. There is no hidden PageRank default boost.
- Cross-shard: until a coordinator publishes one table-wide snapshot, multi-shard requests that use direct metric top-k, metric rerank, or metric projection/order/filter fail closed before fan-out. The internal merge contract (group by query name, validate index/metric/fingerprint/edge scope/generation, sort by score then node key, apply `top_k` after merge, re-enforce `fresh` at fan-in) stays tested for that future.
- Metric order was degree, eigenvector, HITS, then personalized PageRank. Degree came second because it is cheap, deterministic, and non-iterative. Personalized PageRank waits for retention, deletion, and quota controls, because it multiplies score cardinality by scope.
- Before a metric is added, it needs documented graph assumptions, convergence and failure behavior, a key namespace, status metadata, top-k tests, and traversal tests.

### Executor architecture
- There are five internal boundaries. The graph index owns config, fingerprint, dirty marker, published pointer, freshness, and status. The coordinator owns job start/resume, manifest validation, barriers, dynamic iteration planning, verified publish, failure, cleanup scheduling, and duplicate fencing. The worker owns one leased page at a time: claim, renew, cursor, output, complete/fail. The runtime/scheduler owns role, owner identity, budgets, wakeups, and telemetry. The cleanup runner does resumable deletion and never touches the current published generation.
- Hard invariant: workers execute pages and coordinators publish generations. Workers resolve work by index and metric name, never receive caller-supplied metric config, never create jobs, never advance phases, never publish, and never fail a whole build.
- There are three independent fences. Runtime-owner leases fence processes (role-scoped for coordinators, worker-identity-scoped for workers, order-independent worker-id-set-scoped for pools). Page leases fence page execution. Page attempts fence output writes and adoption. Role gates remain enforced even if the lease fence is disabled.
- Transaction rule: any page write that is public or consumable by a later phase must be guarded by the same durable page-attempt validation that completes or adopts the page. If that can't be atomic, the page writes to an attempt namespace (`metric_attempt/<metric>/<job_id>/<phase>/<iteration>/<page_id>/<attempt>/*`) and adopts on completion.
- Deterministic recompute is the default retry strategy. Attempt-scoped adoption is mandatory where later phases could consume partial output: degree scan, iterative contribution pages, and HITS hub raw contribution. Reduce-like phases move to adoption only when tests or workload data show stale-output or recompute risk. Their writes are already fenced by attempt validation.
- Retry, lease, and backoff policy stay internal. The first plan was `max_page_attempts = 3`, the existing local lease timeout, and a fixed small backoff. Exhausted pages make the coordinator fail the active build.
- Planner: idempotent per metric config fingerprint and target edge generation. A changed fingerprint makes the old plan ineligible instead of mutating it. Pages are stable key ranges (reverse-edge, node, and cleanup prefixes), and exact load balance is a non-goal. Later iterations are appended dynamically only after a non-final convergence barrier.
- PageRank phases are `prepare_generation`, `scan_edges_and_out_degree`, `initialize_ranks`, `iterate_contributions`, `reduce_ranks`, `check_convergence`, `publish_generation`, `cleanup_old_generations`. Degree uses prepare/scan/reduce/publish/cleanup.
- HITS was split into explicit retryable phases (`initialize_pair`, authority contribute, authority reduce/norm, hub contribute, hub reduce/norm, paired convergence, paired publish, paired cleanup). Before the split, one reduce page materialized global hub raw state. Authority and hub stay separate named scores but share one target generation, convergence, publish, failure, and cleanup decision.
- Verified publish checks the active job/manifest agreement, config fingerprint eligibility, complete phase summaries and page fingerprints, the convergence summary, score validity (no NaN/inf), and paired-manifest compatibility, all in the same transaction as the pointer flip. Publish advances to `cleanup_old_generations`, so the new generation is queryable while cleanup is pending.
- A failed planned build deletes unpublished score generations and the job namespace and keeps compact failed-job status plus bounded recent failure/event records. Public failure is an active-build operation only, so repeating it on a cleared lease fails as not active.
- A failed planned build is terminal for automatic scheduler restarts at the same target generation. A later dirty generation (or a future explicit retry control) starts new work. Runtime ticks over terminal-only failed work count as idle, not error.
- Process owners get only a DB path or service endpoint, role, owner id, worker id or set, lease TTL, tick/page/metric budgets, idle policy, and an optional test clock. Argv and summaries are allow-listed to exclude metric/index names, target generations, job/page ids, attempt namespaces, storage paths, configs, and pids. Zero TTL or zero budgets are rejected at command and enabled-runtime validation. Duplicate worker ids within one pool are rejected.
- The direct file-backed DB launch path keeps an explicit local writer guard as harness-only behavior, because graph runtime leases are not a storage-engine multi-writer lock. Production orchestration goes through the internal service boundary: `/internal/v1/groups/{group}/tables/{table}/graph-metric-maintenance` with `tick`, `status`, and `release` actions, plus a `MaintenanceBoundary` vtable shared by runtime and command.
- Status/API maturity: generated clients gain a field only once it is a stable summary. The first stable runtime summary is `graph_metric_runtime` on graph index status. If shard runtimes report different roles, aggregate status omits `role` and keeps the counters and hashes. Raw keys, exact owner ids, page ids, attempt namespaces, and writer-guard details stay internal.

### Rollout policy
- Promote by metric family, never all at once: degree (non-iterative canary), then PageRank (reference iterative), then eigenvector (proves the single-vector substrate is generic), then HITS last (paired-vector failure is the highest-risk contract). Local runners stay as deterministic CI/debug oracles until parity is "boring".
- Dependency chain: owner correctness before any default promotion, and cross-shard comparability before score-bearing fan-in promotion. A family must not go distributed-by-default while duplicate coordinators can race publish/fail, stale attempts can write, cleanup can grow, or fan-in can mix incomparable generations.
- The `auto` scheduler gate is conservative. It admits already-active planned work, queued degree, PageRank, and eigenvector within caps, and compatible HITS pairs (counted as one lifecycle). Incompatible HITS and explicit operator/iteration caps fall back to local maintenance. Later revisions say default HITS, larger PageRank/eigenvector, and multi-metric indexes assert fallback unless internally widened or opted in. Raising the internal iteration caps widens single-vector eligibility. Budget exhaustion is a resumable `budget_exhausted` result, not an error.
- Degree canary (`degree_canary` idle mode) admits exactly one queued or active degree build. It blocks when non-degree work is queued or active, rejects failed or truncated page summaries, and enforces a configurable control-record cap, with queued builds estimated before job/page state is created. It falls back to local before starting blocked queued work and fails fast if active planned work is outside the guardrails. Planned results report `rounds_executed`.
- No graph-metric-specific Make/CI targets. Coverage runs in the existing unit-test/integration-test/full-default aggregates, and the rollout runner (`--profile smoke|promotion`) is release tooling that emits JSONL, not a product build target. It must not introduce a public job API.

## Rejected approaches
- A separate job resource per algorithm, a separate HITS query API, or metric-specific job records. All metrics plug algorithm phases into one shared executor, so a new metric contributes math and metadata, not a job system.
- A hidden PageRank boost in ranking. Any metric that changes ordering must be visible in the request, profile, or explain output.
- Planner-level score blending in Phase 1. It was deferred until freshness and distributed merge semantics were tested, then added only as explicit `graph_metric_rerank`.
- Merging independently normalized shard-local scores. Generations that look numerically compatible can still produce wrong global rankings, so these requests fail closed.
- Implicit filter-derived metric names. Arbitrary edge predicates wait for a typed predicate contract.
- Personalized PageRank as the second metric (cardinality and quota risk).
- Exposing retry, lease, or backoff policy as user config in the first distributed version.
- One-page-per-phase manifests. They prove the metadata but don't scale, so they were replaced by deterministic key-range pages.
- Letting a HITS reduce page materialize global hub raw state. Replaced by explicit hub contribute and hub reduce/norm phases with attempt-scoped hub raw output.
- Treating the shared local DB plus writer guard as production orchestration.
- Treating reopen-between-ticks as a substitute for killing owners that hold leases or attempts. It proves durable resume only.
- Baking arbitrary timing, storage, page-count, or retry thresholds into PR CI. Those budget flags stay disabled by default until real baselines exist, and local/planned wall-clock latency is recorded as release notes, not gated.

## Evidence state at end of log
- **Local/DB:** local-vs-planned parity for all four families (including partitioned alternating-worker drains); reopen/cursor-resume, reclaim, failed-page retry, exhausted-attempt failure, publish-verifier failure, and cleanup resume for PageRank, eigenvector, and HITS; threaded concurrent-handle ownership; DB-level production-budget parity via a 130-source one-page-budget planned drain for PageRank, eigenvector, and the HITS pair; and repeated-failed-build storage-growth proofs for all families. Eigenvector parity also covers disconnected/reducible graphs (finite, L2-normalized, sink-chain nodes may decay to zero).
- **Process harness (`antfly graph-metric-maintenance` `supervise`/`launch`):** drains degree, PageRank, eigenvector, and compatible HITS. Kills coordinator, worker, worker-pool, and cleanup owners at every phase (including dynamically planned later iterations with `max_iterations: 2`), checks fencing before expiry, takeover after expiry (`takeover_count`), and stale-attempt rejection, and verifies fixed-iteration metadata and active-rebuild public freshness. It emits `graph_metric_process_harness_summary` with `remote_owner_release_gate: true` (split into service, direct, and failure/reclaim sub-gates) only after every coverage category reaches its required count.
- **Service owners (real HTTP):** restart/replacement for degree, bounded PageRank, eigenvector, and HITS (via `hits_authority`); publish-to-cleanup with duplicate-coordinator idempotence; publish-verifier failure for PageRank, eigenvector, and HITS; active public reads; and 130-source two-worker multi-page builds with killed coordinator and worker-pool timing.
- **Public reads/fan-in:** fast-root merge/profile checks; hosted cross-range fan-in, including a nonuniform eight-shard degree/PageRank/eigenvector direct merge with four active/stale shards and an eight-shard compatible HITS layout with four active/stale shards; and fan-in rejection of missing, zero, stale, duplicate, unrequested, non-finite, out-of-range, identity-mismatched, invalid-state, and incompatible-metadata/edge-filter payloads.

## Remaining work at end of log
- Promotion-scale remote-owner evidence: deployment-sized coordinator plus multiple worker pools, with killed-owner churn at scan, contribution, reduce, publish, and cleanup.
- Promotion-scale hosted cross-shard fan-in (larger and mixed hot/cold layouts, active/stale mixes for rerank and paired HITS, varied incompatible HITS pairs). If a standalone explain API is ever added, it needs matching generation/freshness evidence. Query profile is the current explainable contract.
- Deployment-scale cleanup and storage-growth qualification (larger retained namespaces, longer owner churn), plus latency baselines before any wall-clock gates.
- Per-family default widening (degree, then PageRank, eigenvector, HITS) with docs, generated-client stability, and rollback controls. HITS stays off by default until paired evidence matches the PageRank bar.
