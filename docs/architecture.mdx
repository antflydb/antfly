## Overview

Antfly is a distributed key-value store and vector search engine built on a **multi-Raft consensus architecture**. It combines the best of traditional databases with modern AI capabilities to deliver hybrid search at scale.

## What Makes Antfly Unique

### Hybrid Search

- **BM25 + Vector Similarity**: Full-text search with vector embeddings using Reciprocal Rank Fusion (RRF)
- **Multimodal**: Index and search text, images, and audio with native Antfly models or application-managed vectors
- **Managed Index Embedders**: Antfly Inference, Ollama, OpenAI, OpenRouter, Cohere, Gemini, Vertex AI, and AWS Bedrock

### Distributed Consensus

- **Multi-Raft Design**: Separate consensus groups for metadata (single cluster) and storage (one per shard)
- **Horizontal Sharding**: Tables partitioned by key range across shards with configurable replication
- **Fine-Grained Durability**: Control write consistency with sync levels (propose, write, full_text, enrichments, full_index)

### AI-Native Features

- **RAG**: Streaming retrieval-augmented generation with Server-Sent Events
- **Native Agents**: Retrieval and query-builder agents for bounded query planning, tool selection, and answer generation
- **Document Chunking**: Semantic chunking service (Antfly Inference) with multi-tier caching
- **Async Enrichment**: Background embedding and summarization with leader-only processing

### Developer Experience

- **JSON Schema Extensions**: Custom `x-antfly-*` annotations for indexing
- **MongoDB-Style Transforms**: In-place updates ($inc, $set, $push) without read-modify-write
- **Linear Merge**: Stateless import of sorted records from external sources
- **Template Rendering**: Handlebars templates for custom document rendering
- **Graph Operations**: Declarative queries with traversals and pathfinding

### Flexible Indexing

- **Index Types**: `full_text` (BM25), `embeddings` (dense, sparse, and late-interaction vectors), `graph` (traversal and pathfinding), `algebraic` (aggregates and materializations), `relational` (ordered composite keys over typed rows)
- **Enrichers**: summaries, embeddings, chunking (async background processing)
- **Query Processors**: `chunker` (semantic document splitting), `pruner` (result filtering), `reranker` (relevance re-scoring)
- **Multimodal**: Native ClipClap embeddings, durable extraction, or application-managed vectors
- **Pluggable Architecture**: Easy to add custom index types via registry pattern

## Core Components

### Storage Layer

**Native LSM and LMDB-Compatible Engines**

Antfly's storage engine is implemented natively in Zig (`zig/pkg/antfly/src/storage`). Two engines are available: a native LSM-tree engine (`storage/lsm`) with a write-ahead log, table files, and background compaction, and an LMDB-compatible copy-on-write B-tree engine (`lmdb`). Each shard owns its own storage instance, providing:
- Efficient data storage and retrieval
- Fast range scans
- Reliable crash recovery via write-ahead logging (LSM) or copy-on-write commits (LMDB)

### Consensus and Distribution

**Raft Consensus Algorithm**

Antfly ensures data consistency across nodes using the Raft consensus algorithm:
- Strong consistency guarantees
- Automatic leader election
- Log replication across nodes
- Split-brain prevention

### Multi-Raft Architecture

Unlike single-raft systems, Antfly employs a sophisticated multi-raft design:

- **Shard-Level Consensus**: Each data shard runs its own Raft group
- **Independent Scaling**: Shards can be moved and replicated independently
- **Fault Isolation**: Failures in one shard don't affect others
- **Parallel Operations**: Multiple raft groups can process requests simultaneously

## Data Model

### Document Storage

Antfly stores data as JSON documents with:
- Schema-optional design for flexibility
- Automatic indexing of fields
- Support for nested structures

### Sharding Strategy

Tables are divided into shards by key range, and each shard is replicated by its own Raft group with a configurable replication factor. Size-based automatic split and merge (`max_shard_size_bytes`, default 64 MiB) is opt-in: set `disable_shard_alloc: false` in the shard allocation config to enable it.

## Indexing Architecture

### Full-Text Search

Implemented natively in Zig (`zig/pkg/antfly/src/search`) as a Lucene-style segment index with FST-based term dictionaries and roaring-bitmap postings, our full-text indexing provides:
- Language-aware tokenization
- Fuzzy matching and phrase search
- Faceted search capabilities
- Custom analyzers and filters

### Vector Indexing

Dense vectors are indexed in postings (leaf clusters of vectors) under a hierarchical balanced clustering (HBC) centroid tree (`zig/lib/vectorindex`). Once an index grows past about 1,024 postings, the default `centroid_directory_mode: auto` routes through a flat centroid directory instead of the tree. The index offers:
- Approximate nearest neighbor search that scans the closest leaves, then reranks candidates with exact distances
- Configurable precision/performance tradeoffs (search effort, leaf size, rerank policy)
- Support for high-dimensional vectors
- Incremental updates with [SPFresh](https://arxiv.org/abs/2410.14452)-style local maintenance: an insert touches one posting, oversized leaves split, undersized leaves merge into a sibling, and a background pass moves boundary vectors between sibling leaves. Updates never trigger a full rebuild
- Quantization using [RaBitQ](https://arxiv.org/abs/2405.12497): each leaf stores 1-bit codes of vector residuals against the leaf centroid, and full-precision vectors are kept for reranking

### Hybrid Search Engine

The query engine seamlessly combines both index types:
- Unified scoring across text and vector results
- Query-time weighting of different signals
- Efficient multi-index traversal
- Result deduplication and ranking

## AI Integration

### Embedding Pipeline

- **Plugin Architecture**: Modular design supports multiple embedding providers through a unified interface
- **Batch Processing**: Efficient batching of embedding requests to maximize throughput
- **Caching Layer**: Smart caching of embeddings to reduce API calls and latency
- **Async Processing**: Non-blocking embedding generation with progress tracking

## Reliability Features

### Write-Ahead Logging

Every operation is logged before execution:
- Durability guarantees
- Point-in-time recovery
- Efficient batch commits
- Configurable sync policies

### Write Visibility

Writes commit through the shard's Raft log. Secondary indexes and enrichments are applied asynchronously after commit. The per-request `sync_level` (`propose` by default, then `write`, `full_text`, `enrichments`, and `full_index`) chooses how far a write progresses before the request returns.

## Network Architecture

### Raft Transport

Raft messages and snapshots travel between nodes over HTTP (`zig/pkg/antfly/src/raft/transport`). The peer endpoint schema can describe HTTP/2, HTTP/3, and QUIC endpoints, and the HTTP stack (`zig/lib/httpx`) implements QUIC/HTTP-3, but the Raft transport currently uses HTTP.

### API Design

The REST API is designed for:
- Intuitive resource-based operations
- Streaming support for large responses
- Comprehensive error handling
- OpenAPI specification

## Deployment Modes

### Standalone Mode

For development and small deployments:
- Single binary runs metadata, data, and Antfly Inference
- Zero configuration required

**Minimum Requirements (Standalone Mode):**
- 2 CPU cores
- 4GB RAM
- 20GB storage
- Suitable for small VPS or local development

### Production Mode

For scale and reliability:
- Separate `antfly metadata` and `antfly data` nodes
- Configurable replication topology
- Rolling upgrade capability

**Recommended Requirements (Production):**
- Metadata nodes: 4+ CPU cores, 8GB+ RAM
- Storage nodes: 8+ CPU cores, 16GB+ RAM, SSD storage
- Network: Low-latency connections between nodes

### Other Modes

- **Antfly Lite**: the engine embedded in a single `.aflite` file (`antfly lite`, C ABI bindings)
- **Hot standby**: a single node plus an `antfly standby` replica
- **Serverless**: `antfly serverless` over S3-compatible or GCS object storage

## Performance Optimizations

- **Query Planning**: Cost-based optimizer for complex queries
- **Connection Pooling**: Efficient resource management for concurrent requests
- **Memory Management**: Careful control of memory usage with configurable limits

## Future Architecture Goals

We're continuously evolving Antfly's architecture to:
- Support even larger scale deployments
- Reduce query latency further
