LightOnOCR-3-0.8B and 4B are Apache-2.0 document parsers based on Qwen3.5. Each
transcribes page images into Markdown, including HTML tables and LaTeX formulas.
Antfly uses the integrated safetensors checkpoint with the native Qwen vision
and hybrid-attention decoder paths.

## Install

```bash
antfly inference pull lightonai/LightOnOCR-3-0.8B:safetensors@36d8636925327c671bd8e479c517a004f7566bd9
```

The pull installs the upstream configuration, tokenizer, chat template, image
processor, and weights, plus a `model_manifest.json` declaring generation and
reading. Runtime lookup also accepts `lightonocr3-0.8b`. The checkpoint contains
852,985,920 BF16 parameters, approximately 1.7 GB of weights; working memory is
additional. This integration does not add a Qwen3.5 GGUF weight mapping.

The larger model uses the same image-only prompt and `/read` API:

```bash
antfly inference pull lightonai/LightOnOCR-3-4B:safetensors@b71010f095dc3735de7ee6b9969bff8f8f50b39a
```

Use `lightonocr3-4b` as the model name. Its 4,539,265,536 BF16 parameters
occupy approximately 9.1 GB of weights. It has 32 decoder layers with hidden
size 2560, 16 recurrent key heads and 32 value heads, plus a 24-layer vision
encoder with hidden size 1024. The 0.8B model has 24 decoder layers with hidden
size 1024 and a 12-layer vision encoder with hidden size 768. Both retain
128-channel recurrent heads, four-tap convolution, and partial M-RoPE.

Both Metal models defer paged-attention completion within the active
decoder frame, avoiding a GPU wait at every full-attention layer. The rollback
is `TERMITE_METAL_DISABLE_ACTIVE_PAGED_SLOT_ATTENTION_DEFERRED=1`.

On M4 Max, both projection paths use SIMD reductions for single-token
projections, including the small recurrent gates, and fuses FFN gate/up
projection with SiLU. Its wide decode and attention-head RMS normalizations
also use parallel F32 reductions instead of scanning each row in one lane.
Eligible multi-token projections use Metal 4 TensorOps
on macOS 26.1 or newer. Unsupported shapes, alignment, or shader availability
retain the existing implementation. The master rollback is
`TERMITE_METAL_DISABLE_LIGHTONOCR3_PROJECTIONS=1`.
Normalization alone can be rolled back with
`TERMITE_METAL_DISABLE_LIGHTONOCR3_PARALLEL_NORM=1`.

F32 activations, accumulation, and recurrent state remain the default.
`TERMITE_METAL_LIGHTONOCR3_BF16_ACTIVATIONS=1` experiments with BF16 inputs
only for eligible multi-token TensorOps projections. It preserves F32 outputs
and recurrent state; it does not convert the whole runtime to BF16.

The 4B model automatically sizes its GPU cache and admission envelope from the
weight artifact to cover both mapped source weights and prepared device
weights. Explicit operator memory limits still take precedence. Working memory
is additional to checkpoint size; the local comparison uses 36 GiB of unified
memory.

## Read a page

Send a rendered PDF page or other document image to the inference service:

```bash
curl http://localhost:8080/ai/v1/read \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "lightonocr3-0.8b",
    "images": [{"url": "data:image/png;base64,..."}],
    "max_tokens": 1024
  }'
```

Omit `prompt` or pass an empty string for transcription. This model is trained
with an image-only prompt; a generic instruction such as `Transcribe this page`
is rejected by `/read`. The alternative `"prompt": "grounding"` returns the
model's native labeled bounding-box markers, descriptions, and chart tables in
the result's `text`. These markers use coordinates normalized to 0–1000; they
are not converted into pixel-coordinate `regions`.

On Metal, `/read` coalesces compatible pages from the same request and from
concurrent requests into bounded cohorts. Decoder projections share GPU work;
each page keeps independent KV, DeltaNet history, and image positions. Pages
retire independently inside the cohort. Vision projection and prefill retain
the shared runtime's execution lock. CPU and CUDA readers retain serial page
execution. Response execution counters report pages that actually participated
in a multi-page decode step.

`/read` currently accepts at most 1024 output tokens
per page and rejects truncated output. Use `/generate` with a larger budget
for dense pages; its content should contain the image and either no text or
the exact `grounding` keyword, with thinking disabled.

## Resolution and validation

The runtime reads pixel limits and patch geometry from the installed image
processor, bounded by a runtime cap of 4096 merged vision tokens per image,
and uses the same geometry for admission and execution. Resize page
images before submitting them when optimizing latency; the upstream speed
evaluation includes a 1540-pixel-long-side setting. Higher-resolution results
must be measured separately.

The shared Qwen vision path supplies learned image-position embeddings and
two-axis vision rotary positions. Qwen3.5's full-attention layers use three-axis
M-RoPE on the first 64 channels of each 256-channel head, preserving the tail;
its remaining layers use recurrent linear attention. LightOn has no DeepStack
vision taps. On Metal, the qualified 128-channel, four-tap DeltaNet path keeps
causal convolution, normalized Q/K, gates, recurrent matrices, and gated RMSNorm
on-device. Prefill distributes each value column across a 32-lane SIMD group;
single-token decoding uses a separate kernel. Buffers belong to the request,
and reset invalidates their history before reuse. The numerical test covers
short prefixes, grouped heads, continued decoding, reset, and zero core
readbacks against the CPU reference.

Metal batches decoder commands across layers and vision commands within each
block. The M4 Max also enables vectorized BF16 weight loads for the qualified
0.8B and 4B text/vision projection shapes; activations and accumulation remain F32.
Other shapes retain the existing dispatch. The CPU fallback uses vectorized
recurrence and activations. Measure release-build latency on deployment
hardware before setting an SLO; this does not qualify CUDA or vLLM throughput.

```bash

```

Add `--profile-phases` for an additional instrumented request reporting vision,
language prefill, decode, and output-head timings. Instrumentation is excluded
from the ordinary warm samples. MPS event intervals include device queue idle
time; nested forward scopes must not be added together.

The four bundled synthetic pages also exercise receipts, letters, and shipping
labels. Compare a ReleaseFast inference test executable against Transformers:

```bash
uv run zig/pkg/inference/scripts/lightonocr3/benchmark_corpus.py \
  --native-test /absolute/path/to/inference-test-executable \
  --model-dir /absolute/path/to/4b-model \
  --modes baseline f32 bf16 --warm-runs 3 \
  --timeout-seconds 180 \
  --output-dir /tmp/lightonocr3-corpus
```

This runs each runtime sequentially and saves raw logs, latency, transcription,
required-string coverage, and whitespace-normalized character error rates.
Repeat with `--pytorch-first` to reverse runtime order. Markdown formatting
affects the raw character error rate; a separate content-only metric strips
HTML tags, Markdown headings, and bold markers. These pages are smoke
tests, not a representative OCR accuracy benchmark. `baseline` disables the
new 4B kernels; `bf16` rounds eligible multi-token projection inputs
while preserving F32 recurrent state and accumulation.
Each subprocess defaults to a 600-second timeout. The process envelope is
configurable with `--process-limit-gib`; larger pages may need more room than
the invoice. Live physical-memory admission remains active.

The reference uses BF16 weights, MPS, SDPA, greedy decoding, caching, the upstream
image-only chat template with thinking disabled, and a 128-token output limit.
It reports loading separately, one cold generation and three warm generations,
including image preprocessing. Both use the original 1200×360 image, which
resizes to 1216×352 and yields 418 merged image tokens. The native comparison
uses the direct encoded-image `/read` implementation without HTTP overhead.
These runs measure a small transcription example, rather than dense-page
throughput or corpus accuracy. MPS does not exercise CUDA's optional fused
recurrent-attention kernels.

On an Apple M4 Max with 36 GiB unified memory (2026-10-21), two adjacent
native/PyTorch rounds produced the following six warm requests per runtime:

| Runtime | Warm range | Median |
| --- | --- | --- |
| Antfly ReleaseFast, Metal | 0.859–0.868 s | 0.865 s |
| PyTorch 2.14.1 / Transformers 5.5.4, BF16 MPS | 0.888–1.077 s | 1.033 s |

Native median latency was approximately **16% lower** (1.20× speedup).
Every run returned identical invoice text. Each request recomputed the image
and generation. These are shared-machine results on one small invoice;
dense-page throughput, grounding performance, corpus accuracy, and CUDA remain
unqualified. The reference uses BF16, while native activations and accumulation
remain F32. This verifies text agreement on the fixture, rather than full
PyTorch token/logit parity.

The initial Metal implementation took 10.58–11.08 seconds warm. The earlier
26-second CPU baseline came from a benchmark setup mistake: its embedded-node
defaults disallowed process-required GPU backends before model loading. The
checkpoint test now attaches the supervised-node I/O and cancellation runtime;
the command above requires Metal so it cannot silently fall back.

The original 0.8B qualification passed 17 focused tests, including GPU/CPU
agreement for prefill, continued decoding,
grouped heads, reset, and zero core readbacks. A separate independent native
Metal check measured maximum output error below 5×10⁻⁷ and state error below

Raw paired measurements, generation phase timings, configuration and reference

Times include image preprocessing, inference, and output handling; HTTP,

The inputs and output budgets match, but precision and model-native resizing

## Concurrent reader throughput

The native Metal reader supports concurrent `/read` calls and the linked
encoded-image API. Single-page latency and saturated serving throughput measure
different things. Whole-reader vLLM parity remains unfinished for LightOn.

Qualified M4 readers refill finished page slots while peers keep decoding. Each
page owns its KV, recurrent history, image positions, deadline and cancellation.
The default active window and decode-row cap are eight. Qualified M4 opt-ins
can widen physical decode and the active window to sixty-four independent
pages. An ordinary epoch accepts sixty-four page admissions; the extended
epoch option accepts up to 256 admissions while retaining the same live window. Pages
queue before per-run GPU allocation. Hard memory limits remain authoritative;
transient page admission pressure retries for at most thirty seconds without a
resource lease. Full multimodal prefill must fit its admitted prompt envelope.
`/generate` and `/generate/batch` retain their existing scheduling behavior.

### Settings

| Setting | Default | Purpose |
| --- | --- | --- |
| `ANTFLY_LIGHTONOCR3_BATCH` | `1` | Set `0` for the serial reader implementation. |
| `ANTFLY_LIGHTONOCR3_CONTINUOUS` | Qualified M4: `1`; otherwise `0` | Refill completed slots; `0` restores fixed waves. |
| `ANTFLY_LIGHTONOCR3_BATCH_ROWS` | Qualified M4: `8`; otherwise `4` | Maximum pages sharing a decode step; clamped to the enabled physical row ceiling. |
| `ANTFLY_LIGHTONOCR3_BATCH_WINDOW` | `8` | Maximum active pages; the default implementation permits up to sixteen, and qualified wider profiles permit up to sixty-four. |
| `ANTFLY_LIGHTONOCR3_BATCH_WAIT_US` | `5000` | Fixed-wave collection wait; capped at 20000 microseconds, with the node wait as a floor. |
| `ANTFLY_LIGHTONOCR3_DISABLE_SHARED_VISION_PEAK` | `0` | Set to `1` to restore per-page vision peak reservations; experimental batched vision always keeps those reservations. |
| `ANTFLY_LIGHTONOCR3_DECODE_WAIT_US` | Node setting, normally `1000` | Decoder collection wait; capped at 10000 microseconds. |
| `TERMITE_METAL_ENABLE_LIGHTONOCR3_WEIGHT_RESIDENCY` | `0` | Wire existing admitted dense weights before preparation, without copies; bounded to 12 GiB and 32 sets. |
| `ANTFLY_LIGHTONOCR3_VISION_BATCH` | `0` | Experimental grouping of up to four pages with equal resized geometry. |
| `ANTFLY_LIGHTONOCR3_PREFILL_BATCH` | `0` | Experimental grouping of up to four equal-length prepared prompts. |
| `ANTFLY_LIGHTONOCR3_VISION_WAIT_US` | `2000` | Experimental vision collection wait; capped at 100000 microseconds. |
| `ANTFLY_LIGHTONOCR3_PREFILL_WAIT_US` | `5000` | Experimental prefill collection wait; capped at 100000 microseconds. |

The early throughput configuration below uses eight rows, an eight-page window
and opt-in weight residency. Later execution-engine experiments use wider
physical batches, prepared decode, GPU recurrent state and shared scratch.
[Current execution evidence](https://github.com/antflydb/antfly/tree/feat/lightonocr3-08b/zig/pkg/inference/scripts/lightonocr3/results/throughput_engine_m4_max)
records the full settings, source and binary identities, rejected candidates,
and matched reference runs. Larger collection windows trade request latency
for batch occupancy; measure representative pages before selecting a profile.

```bash
export ANTFLY_LIGHTONOCR3_BATCH_ROWS=8
export ANTFLY_LIGHTONOCR3_BATCH_WINDOW=8
export TERMITE_METAL_ENABLE_LIGHTONOCR3_WEIGHT_RESIDENCY=1
```

Batched vision keeps attention lanes separate and splits projected embeddings
back to their page owners. Prepared-prompt batching carries complete axis-major
M-RoPE positions and independent KV/recurrent states; it does not pad queries.
The short default waits often formed singleton batches. Longer experimental
waits have separate measurements and remain explicit options. Final
default/combined/default controls did not show a reproducible throughput gain
from longer waits; 4B was slower with the combined setting.

### Experimental execution options

`ANTFLY_LIGHTONOCR3_THROUGHPUT=1` enables the qualified M4 serving preset for
prepared weights, the dedicated decode executor, event waits, activation reuse,
CPU image preparation and an extended epoch. It defaults to sixteen physical
rows; explicit settings still take precedence. It preserves checkpoint weights,
decoder precision, operator caps and the live memory reserve.

The wider and pipelined paths remain separate opt-ins:

| Setting | Default | Purpose |
| --- | --- | --- |
| `ANTFLY_LIGHTONOCR3_PREFILL_ACTIVATION_POOL` | `0` | Retain up to 64 MiB of completed private prefill/decode buffers instead of the 8 MiB decode-only cache. The full cache is reserved once per admitted epoch; unfinished frames remain fenced. Experimental; measure whole-reader throughput before selecting it. |
| `ANTFLY_LIGHTONOCR3_PACKED_MIXED` | `0` | Pack bounded prefill and decode tokens into shared projections while preserving each page's positions, KV cache and recurrent history. Requires qualified prepared Metal execution, GPU recurrent state and shared scratch. |
| `ANTFLY_LIGHTONOCR3_PACKED_PREFILL_ITEMS` | `1` | Bound packed prefills per scheduler step to 1–8 pages; the shared admission envelope includes the corresponding prompt working sets. |
| `TERMITE_METAL_ENABLE_LIGHTONOCR3_WIDE_RECURRENT` | `0` | With shared recurrent weights and qualified pipelines, collect up to 64 recurrent decode rows. Larger argument tables use frame-owned staging; unsupported layouts retain the bounded fallback. |
| `ANTFLY_LIGHTONOCR3_PHYSICAL32` / `ANTFLY_LIGHTONOCR3_PHYSICAL64` | `0` | Widen qualified physical decode to 32 or 64 rows; the 64-row option takes precedence. |
| `ANTFLY_LIGHTONOCR3_LOGICAL64` | `0` | Permit a 64-page live window with the physical32 path. Physical64 already permits this window. |
| `ANTFLY_LIGHTONOCR3_DEVICE_RECURRENT_STATE` | `0` | Retain each page's convolution and recurrent matrices solely on the qualified GPU path; an unsupported core fails before host fallback. |
| `ANTFLY_LIGHTONOCR3_SHARED_DECODER_SCRATCH` | `0` | With prepared decode, epoch resources and GPU recurrent state, reserve a shared peak for the serialized decoder rather than a full working set per waiting page. |
| `ANTFLY_LIGHTONOCR3_KEEP_VISION_WORKSPACE` | `0` | Keep vision packing banks under the epoch's retained vision lease. |
| `ANTFLY_LIGHTONOCR3_RESIDENT_VISION_BUDGET` | `0` | Require the closed resident vision implementation before admitting its bounded linear workspace. |
| `ANTFLY_LIGHTONOCR3_SHARED_CORE_WEIGHTS` | M4 4B throughput preset: `1`; otherwise `0` | Share immutable recurrent side weights within the admitted epoch; required for prompt streaming. |
| `ANTFLY_LIGHTONOCR3_SINGLE_FRAME` | `0` | Keep decoder, output head and argmax in one owned frame; required for complete-step token bursts. |
| `ANTFLY_LIGHTONOCR3_GPU_TOKEN_BURST` | `0` | Pipeline complete greedy decode steps with GPU token handoff; requires prepared decode, the executor, GPU recurrent state, shared scratch and single-frame mode. Set `ANTFLY_LIGHTONOCR3_STREAM_FIRST_LAYERS=0` when selecting it. |
| `ANTFLY_LIGHTONOCR3_GPU_TOKEN_BURST_WIDTH` | `2` | Bound each burst to 2–8 steps and to every page's remaining token capacity. Larger bursts reduce scheduler handoffs and can delay token publication. EOS and cancellation discard unused results after producers drain. |
| `ANTFLY_LIGHTONOCR3_PIPELINE_VISION` | `0` | With resident vision and CPU preparation, overlap two fully admitted single-image frame groups. Group size must be one or two blocks. |
| `ANTFLY_LIGHTONOCR3_PREFILL_STREAM_LAYERS` | `0` | Experiment with prompt layer groups of 1–16 after one complete synchronous prompt; currently limited to single-page prompts up to 1024 tokens, shared core weights and shared decoder scratch. |

Prompt streaming and token bursts use the existing two frame banks. The
combined host/device bounds, per-page KV/history reservations and output
ownership remain enforced. Prompt streaming preserves prefill precision and
requires active-frame packing reuse; explicit rollback or concurrent planned
encoding disables that option. The benchmark exposes these paths through
`--physical64`, `--device-recurrent-state`, `--share-decoder-scratch`,
`--gpu-token-burst`, `--gpu-token-burst-width`, `--resident-vision-budget`,
`--pipeline-vision` and `--prefill-stream-layers`. Requested settings alone do
not establish a speedup: inspect actual execution counters and exact output
checks in each report.

### Measurement

Build the inference test executable with Zig 0.17, `-Doptimize=ReleaseFast`,
`-Dstrip=true` and `-Dtest-filter=LightOnOCR3`, then use:

```bash
python3 zig/pkg/inference/scripts/lightonocr3/benchmark_concurrency.py \
  --native-test /path/to/compiled/inference-test \
  --model lighton08=/path/to/LightOnOCR-3-0.8B \
  --images zig/pkg/inference/src/models/testdata/lightonocr3/invoice.png \
    zig/pkg/inference/scripts/lightonocr3/corpus/receipt.png \
    zig/pkg/inference/scripts/lightonocr3/corpus/shipping.png \
  --max-tokens 256 --requests 16 --concurrency 8 --modes batch \
  --continuous --batch-rows 8 --batch-window 8 --weight-residency \
  --memory-gib 24 --shared-memory-gib 28 --backend-memory-gib 16 \
  --kv-memory-gib 4 --scratch-memory-gib 4 \
  --output-dir /tmp/lighton-concurrency
```

Add `--require-small-tail-fusion` to assert actual two-/three-/four-row fused
FFN dispatches, including warmup; tracing affects timing. Without `--continuous`,
the harness forces fixed waves as a control. Add
`--vision-batch --prefill-batch --vision-wait-us 100000 --prefill-wait-us 100000`
to measure the longer experimental windows. Change the model path to test 4B.

The runner launches one resident Node per setting. Loading and serial reference
reads precede timing. Each timed output must match its own serial result
exactly. Reports contain pages/s, p50/p95 latency, batching counters, checkpoint,
image and executable fingerprints, hardware and raw logs. Native timing covers
preprocessing, queueing, inference and text decoding; it excludes HTTP, PDF
rendering and indexing. vLLM reference timing also includes loopback HTTP.
Reference prefix and processor caches are disabled. Each request has a unique
media UUID, preventing reuse of cached image embeddings.

Measurements use a shared M4 Max with 36 GiB unified memory, sixteen repeated
pages and greedy generation with a 256-token ceiling. Machine load changes
substantially between runs. The three synthetic fixtures test consistency,
not real-document OCR accuracy. Native LightOn uses original BF16 weights with F32 outputs, accumulation and
recurrent state. The throughput candidate enables
`TERMITE_METAL_LIGHTONOCR3_BF16_PREFILL_INPUTS=1` for eligible prefill
projection operands, including decode tokens attached to a mixed step; pure
decode operands remain F32 unless the separate BF16 activation option is set.
MLX uses BF16 activation/output storage. Native Florence uses Q4_K weights and F16 encoder
mirrors with no-repeat n-gram size three; its MLX reference uses original FP16
and its greedy policy. These are not fully precision-matched comparisons.

### Kernel qualification

The production path uses model-scoped projections, fused gate/up and SiLU × up,
frame-owned split scratch, SIMD recurrent decode, four-column recurrent prefill
and register-cached F32 normalization. Qualified partial QKV/down projections
use finer K splits while retaining the earlier split if scratch is smaller.
Unsupported dimensions, offsets and missing pipelines retain working fallbacks.
Eligible split dispatches close a planned encoder only after validating its
resources, preserving producer ordering and the outer scope lifetime. Decoder
threadgroup reductions add no persistent scratch. Qualified vision attention
packs the existing half Q/K/V values once and uses TensorOps; its bounded pair
of workspaces is admission-charged and released when its command-buffer owner
retires. Backend teardown also clears any remaining workspace before releasing
the request lease. The 0.8B and 4B vision paths qualify their actual 12- and
16-head architectures separately.

The paired benchmark alternates native and MLX in one process, synchronizes
every sample and checks full outputs plus independent CPU samples. Candidate
comparisons balance all six candidate/production/MLX trial orders. The
`--suite decode-shapes` sweep covers 146 cases: fifteen observed decoder
projection widths at rows one through eight, fused gate/up, vocabulary heads
and normalization/recurrent prefill. The separate 81-case
`--suite page-shapes` sweep covers actual vision, merger and language-prefill
dimensions. The historical 86-case `all-rows` suite omitted several frequently
used decoder widths and cannot establish parity on its own. Primitive results do not prove
whole-reader parity.

Existing individual projection/precision rollbacks remain available. The

On qualified M4 hardware, Florence collects compatible pages for up to five
milliseconds; `ANTFLY_FLORENCE2_BATCH_WAIT_US=0` restores the generic wait.

Current measurements, source/binary manifests, numerical checks, failed
admission attempts and rejected candidates are retained in
`zig/pkg/inference/scripts/lightonocr3/results/throughput_parity_m4_max/README.md`.
Final production sweeps, rollback controls and nearby reference runs are
identified separately from candidate experiments. New narrow recurrent gates
and additional decoder projection widths preserve F32 activations, accumulation
and outputs. Use `--require-decode-projections`, `--require-prefill-gates` and
`--require-vision-mpp` on a diagnostic run to verify that those routes execute;
tracing affects timing. Previous refill measurements remain in `throughput_refill_m4_max`.
Earlier rounds remain archived under `kernel_saturation_m4_max`,
`projection_parity_m4_max` and `concurrent_readers_m4_max` in the same results

adapter and is recorded separately.

The experimental `--prefill-fused-ffn --bf16-prefill-inputs` benchmark flags enable a packed BF16 FFN for 4B prefill rows 128–1024 on qualified Metal devices. The path preserves the existing BF16 prefill operands and F32 output. `--require-prefill-fused-ffn` checks that every timed round used it. It is disabled by default; `TERMITE_METAL_DISABLE_LIGHTONOCR3_PREFILL_FFN=1` restores the ordinary FFN. Full-model qualification returned matching fixture text but was slower than the ordinary FFN, so this remains an experimental option.
