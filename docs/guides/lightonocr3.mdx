LightOnOCR-3-0.8B and 4B are Apache-2.0 document parsers based on Qwen3.5. Each
transcribes page images into Markdown, including HTML tables and LaTeX formulas.
Antfly uses the integrated safetensors checkpoint with the native Qwen vision
and hybrid-attention decoder paths.

## Install

```bash
antfly inference pull lightonai/LightOnOCR-3-0.8B:safetensors@36d8636925327c671bd8e479c517a004f7566bd9
```

The pull installs the upstream configuration, tokenizer, chat template, image
processor, and weights, plus a `model_manifest.json` declaring generation and
reading. Runtime lookup also accepts `lightonocr3-0.8b`. The checkpoint contains
852,985,920 BF16 parameters, approximately 1.7 GB of weights; working memory is
additional. This integration does not add a Qwen3.5 GGUF weight mapping.

The larger model uses the same image-only prompt and `/read` API:

```bash
antfly inference pull lightonai/LightOnOCR-3-4B:safetensors@b71010f095dc3735de7ee6b9969bff8f8f50b39a
```

Use `lightonocr3-4b` as the model name. Its 4,539,265,536 BF16 parameters
occupy approximately 9.1 GB of weights. It has 32 decoder layers with hidden
size 2560, 16 recurrent key heads and 32 value heads, plus a 24-layer vision
encoder with hidden size 1024. The 0.8B model has 24 decoder layers with hidden
size 1024 and a 12-layer vision encoder with hidden size 768. Both retain
128-channel recurrent heads, four-tap convolution, and partial M-RoPE.

Both Metal models defer paged-attention completion within the active
decoder frame, avoiding a GPU wait at every full-attention layer. The rollback
is `TERMITE_METAL_DISABLE_ACTIVE_PAGED_SLOT_ATTENTION_DEFERRED=1`.

On M4 Max, both projection paths use SIMD reductions for single-token
projections, including the small recurrent gates, and fuses FFN gate/up
projection with SiLU. Its wide decode and attention-head RMS normalizations
also use parallel F32 reductions instead of scanning each row in one lane.
Eligible multi-token projections use Metal 4 TensorOps
on macOS 26.1 or newer. Unsupported shapes, alignment, or shader availability
retain the existing implementation. The master rollback is
`TERMITE_METAL_DISABLE_LIGHTONOCR3_PROJECTIONS=1`.
Normalization alone can be rolled back with
`TERMITE_METAL_DISABLE_LIGHTONOCR3_PARALLEL_NORM=1`.

F32 activations, accumulation, and recurrent state remain the default.
`TERMITE_METAL_LIGHTONOCR3_BF16_ACTIVATIONS=1` experiments with BF16 inputs
only for eligible multi-token TensorOps projections. It preserves F32 outputs
and recurrent state; it does not convert the whole runtime to BF16.

The 4B model automatically sizes its GPU cache and admission envelope from the
weight artifact to cover both mapped source weights and prepared device
weights. Explicit operator memory limits still take precedence. Working memory
is additional to checkpoint size; the local comparison uses 36 GiB of unified
memory.

## Read a page

Send a rendered PDF page or other document image to the inference service:

```bash
curl http://localhost:8080/ai/v1/read \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "lightonocr3-0.8b",
    "images": [{"url": "data:image/png;base64,..."}],
    "max_tokens": 1024
  }'
```

Omit `prompt` or pass an empty string for transcription. This model is trained
with an image-only prompt; a generic instruction such as `Transcribe this page`
is rejected by `/read`. The alternative `"prompt": "grounding"` returns the
model's native labeled bounding-box markers, descriptions, and chart tables in
the result's `text`. These markers use coordinates normalized to 0–1000; they
are not converted into pixel-coordinate `regions`.

On Metal, `/read` coalesces compatible pages from the same request and from
concurrent requests into bounded cohorts. Decoder projections share GPU work;
each page keeps independent KV, DeltaNet history, and image positions. Pages
retire independently inside the cohort. Vision projection and prefill retain
the shared runtime's execution lock. CPU and CUDA readers retain serial page
execution. Response execution counters report pages that actually participated
in a multi-page decode step.

`/read` currently accepts at most 1024 output tokens
per page and rejects truncated output. Use `/generate` with a larger budget
for dense pages; its content should contain the image and either no text or
the exact `grounding` keyword, with thinking disabled.

## Resolution and validation

The runtime reads pixel limits and patch geometry from the installed image
processor, bounded by a runtime cap of 4096 merged vision tokens per image,
and uses the same geometry for admission and execution. Resize page
images before submitting them when optimizing latency; the upstream speed
evaluation includes a 1540-pixel-long-side setting. Higher-resolution results
must be measured separately.

The shared Qwen vision path supplies learned image-position embeddings and
two-axis vision rotary positions. Qwen3.5's full-attention layers use three-axis
M-RoPE on the first 64 channels of each 256-channel head, preserving the tail;
its remaining layers use recurrent linear attention. LightOn has no DeepStack
vision taps. On Metal, the qualified 128-channel, four-tap DeltaNet path keeps
causal convolution, normalized Q/K, gates, recurrent matrices, and gated RMSNorm
on-device. Prefill distributes each value column across a 32-lane SIMD group;
single-token decoding uses a separate kernel. Buffers belong to the request,
and reset invalidates their history before reuse. The numerical test covers
short prefixes, grouped heads, continued decoding, reset, and zero core
readbacks against the CPU reference.

Metal batches decoder commands across layers and vision commands within each
block. The M4 Max also enables vectorized BF16 weight loads for the qualified
0.8B and 4B text/vision projection shapes; activations and accumulation remain F32.
Other shapes retain the existing dispatch. The CPU fallback uses vectorized
recurrence and activations. Measure release-build latency on deployment
hardware before setting an SLO; this does not qualify CUDA or vLLM throughput.

Run the focused tests from `zig/` with the repository's Zig 0.17 toolchain:

## Native Antfly reader comparison

A subsequent comparison at runtime revision `b037bec202` used the same native
encoded-image reader API for Florence-2-base Q4_K and both LightOn models.
The shared M4 Max had 36 GiB of unified memory. Each page received six warm
requests across two opposite model orders, with one resident model at a time.
Times include image preprocessing, inference, and output handling; HTTP,
PDF rendering, embedding, and indexing are excluded.

| Model | Weight bytes, decimal GB | Invoice median | Receipt median | Letter median | Shipping median |
| --- | ---: | ---: | ---: | ---: | ---: |
| Florence-2-base Q4_K | 0.142 | 0.400 s | 0.556 s | 0.488 s | 0.505 s |

| LightOnOCR-3-4B BF16 | 9.079 | 1.885 s | 9.600 s | Resource limit | 4.288 s |

The inputs and output budgets match, but precision and model-native resizing

## Concurrent reader throughput

Single-page latency and saturated serving throughput measure different things.
The earlier serial comparison above does not measure Antfly under concurrent
load. Use the concurrency runner to compare the serial implementation with
native batching on the same checkpoint, pages, output budget, and machine:

```bash
python3 zig/pkg/inference/scripts/lightonocr3/benchmark_concurrency.py \
  --native-test /path/to/compiled/inference-test \
  --model lighton08=/path/to/LightOnOCR-3-0.8B \
  --model lighton4=/path/to/LightOnOCR-3-4B \
  --images zig/pkg/inference/src/models/testdata/lightonocr3/invoice.png \
    zig/pkg/inference/scripts/lightonocr3/corpus/receipt.png \
    zig/pkg/inference/scripts/lightonocr3/corpus/shipping.png \
  --max-tokens 256 --requests 16 --concurrency 1 2 4 8 \
  --batch-rows 4 --batch-window 8 \
  --output-dir /tmp/lighton-concurrency
```

Build the native test executable with Zig 0.17, `-Doptimize=ReleaseFast`,
`-Dstrip=true`, and `-Dtest-filter=LightOnOCR3`. The runner launches one Node
per setting and submits concurrent requests to that resident Node. Loading and
serial reference reads finish before the timed region. Every timed output
must match its same-model serial reference exactly. The JSON report includes
wall-clock pages/s, request p50/p95 latency, actual batching counts, model sizes,
image and executable hashes, hardware, and raw logs. It excludes HTTP, PDF
rendering, and indexing. Other machine workloads are uncontrolled.

On the qualified M4 Max, small decoder batches also use vectorized BF16
projection kernels that reuse weights across two to eight rows. Inputs,
accumulation, and recurrent state remain F32. Small 0.8B batches use parallel
normalization reductions. Other devices, missing pipelines, and unsupported
alignment retain the existing dispatcher. For a kernel-only ablation, pass
`--disable-batch-projections` to the runner or set
`TERMITE_METAL_DISABLE_LIGHTONOCR3_BATCH_PROJECTIONS=1` in the server.

The Metal reader enables batching by default. Server process settings:

| Setting | Default | Purpose |
| --- | --- | --- |
| `ANTFLY_LIGHTONOCR3_BATCH` | `1` | Set `0` for the serial implementation. |
| `ANTFLY_LIGHTONOCR3_BATCH_ROWS` | `4` | Maximum pages sharing a decoder step; clamped to 1–8. |
| `ANTFLY_LIGHTONOCR3_BATCH_WINDOW` | `8` | Maximum resident pages in one cohort; clamped to 1–16. |
| `ANTFLY_LIGHTONOCR3_BATCH_WAIT_US` | `5000` | Coalescing window in microseconds; capped at 20000, with the node microbatch wait as a floor. |
| `ANTFLY_LIGHTONOCR3_DECODE_WAIT_US` | Node decode wait (normally `1000`) | Bounded wait for a full decoder step; capped at 10000. Set `0` for eager partial steps. |

The broker groups only the same loaded model generation, prompt, and output
budget. It honors configured media limits and waits up to the configured
coalescing window for compatible pages. Admission accounts every page's KV, recurrent history, retained prompt, and
decoder scratch, plus one serialized vision working set. A capacity failure, including live-memory pressure, splits the cohort before
execution. The decoder coalescing gate applies to every participant, so a follower
cannot bypass the wait and launch a partial step. The target shrinks as pages
finish. These are bounded cohorts: completed pages do not admit replacement
pages until the entire cohort retires. Waiting cohorts queue before taking memory leases. Existing process limits
and live-memory checks remain authoritative. Larger cohorts may require a
larger explicit process envelope and can increase request latency. Sweep both
batch rows and concurrency on representative pages to select the best setting.

`/generate` and `/generate/batch` retain their existing scheduling behavior;
these reader optimizations apply to `/read` and its linked encoded-image API.


The recurrent decode kernels also distribute Q/K and gated RMS normalization
across a SIMD group on the qualified M4 Max. Set
`TERMITE_METAL_DISABLE_QWEN35_CORE_PARALLEL_NORM=1` to restore the scalar
normalizations. Multi-page recurrence shares five encoder stages while keeping
all page histories independent; its rollback is
`TERMITE_METAL_DISABLE_QWEN35_CORE_BATCH=1`. Qualified decoder shapes also reuse input vectors across two or four output
columns, with an exact shader specialization for each batch size from two to
eight. `TERMITE_METAL_DISABLE_LIGHTONOCR3_TILED_PROJECTIONS=1` restores the earlier
vector kernels. Selected eight-row shapes retain the existing F32-input
TensorOps path ahead of tiling; other qualified shapes can use it as a fallback; `TERMITE_METAL_DISABLE_LIGHTONOCR3_SMALL_MPP=1` disables
that fallback. `TERMITE_METAL_LIGHTONOCR3_SMALL_MPP=1` forces an experimental
small-row TensorOps comparison.

Florence-2 Metal readers now queue cohorts before memory admission and provider
acquisition. On qualified M4 devices, encoders prepare bounded F16 mirrors
of quantized linear weights (32 MiB per weight) from the first request. This
throughput policy can increase single-page latency and memory use. Incremental
decoding keeps its existing policy. Set `TERMITE_METAL_FLORENCE2_ENCODER_MIRRORS=0` to roll
back this encoder optimization. Operator memory limits still apply. An eight-page
Florence batch can need a larger scratch reservation than four pages because
admission also covers the full-prefix decoder fallback.

### Kernel optimization follow-up

Qualified M4 kernels now fuse single-token recurrent convolution, normalization,
gates, state update and output normalization. Request-owned recurrent history
and side weights use fresh storage so small persistent tensors cannot retain
oversized prefill buffers. The 0.8B decoder also calls the single-token FFN
fusion. Smaller F32-input TensorOps tiles cover gate/up projections at seven/eight
rows for 0.8B and four through eight rows for 4B, plus both models' QKV
projections at four through eight rows. Florence channel-score reductions and
window softmax distribute work across SIMD groups.

Global LightOn decode attention uses a separate split-K SIMD matrix path for
head dimension 256, the supported 8/2 and 16/4 query/KV head counts, and contexts
192–2048. This path rounds query/probability tiles to F16, with F32 accumulation
and output. Recurrent state and projection activations remain F32 by default.
Unsupported geometry, hardware or missing pipelines keep the previous paths.
These isolated kernel gains do not establish whole-page parity.

Measurements, checkpoint hashes, ablations and reproduction instructions are in
`zig/pkg/inference/scripts/lightonocr3/results/kernel_parity_m4_max/README.md`.
The final follow-up runs reached 1.58/0.49/3.71 pages/s for 0.8B/4B/Florence,
versus refreshed references of 2.99/0.85/5.12. Parity remains unfinished.
These are successive runs on a busy machine with differing precision and
Florence generation policies, not controlled paired comparisons.
Three synthetic fixtures check output consistency; they do not establish OCR
accuracy across real documents. Live-memory admission remains active, including
for the successful 4B throughput runs.

Kernel rollback switches are:

- `TERMITE_METAL_DISABLE_QWEN35_FUSED_DECODE=1`
- `TERMITE_METAL_DISABLE_BF16_FUSED_GATE_UP=1`
- `TERMITE_METAL_DISABLE_LIGHTONOCR3_FFN_SMALL_TILE=1`
- `TERMITE_METAL_DISABLE_LIGHTONOCR3_QKV_SMALL_TILE=1`
- `TERMITE_METAL_DISABLE_LIGHTONOCR3_GQA_SPLIT=1`
- `TERMITE_METAL_DISABLE_FLORENCE2_CHANNEL_REDUCTION=1`
- `TERMITE_METAL_DISABLE_FLORENCE2_WINDOW_SOFTMAX=1`

The concurrency runner exposes matching ablation arguments. Its experimental
`--prefill-sg-attention` selects the existing F16-tiled prefill kernel;
`--bf16-prefill-inputs` rounds only bulk projection inputs (32 or more rows),
while preserving the small-row F32 decode kernels. These options are opt-in;
validate throughput and output on representative documents before selecting them.

On qualified M4 hardware, Florence readers collect compatible pages for up to
5 ms before acquiring the provider. A full cohort executes immediately.
`ANTFLY_FLORENCE2_BATCH_WAIT_US=0` restores the configured generic collection
window (normally 200 µs); explicit reader overrides are capped at 20 ms.
This adds a small bounded wait to sparse requests and reduces underfilled
cohorts under concurrent load. `benchmark_concurrency.py --florence-batch-wait-us`
controls this independently of the LightOn window. `--profile-reader` enables
reader phase logs in the opt-in checkpoint test.

### Projection and encoder follow-up

The next M4 Max kernel pass adds split-K down projections using existing
frame-owned scratch, narrower four-row gate/up and QKV tiles, and vectorized
prefill convolution. F32 projection activations, accumulation and outputs are
preserved. Large qualified F16 encoder projections, including Florence's
vision/BART shapes, use TensorOps with fused bias and retain MPS fallbacks.

In the earlier separate-process M4 Max sweep, 29 of 30 representative
projection cases measured within 20% of MLX or faster. The paired follow-up
below provides stronger evidence and exposes additional cache-sensitive gaps. This excludes the vocabulary head and does not establish
whole-reader parity. The final Florence repeat reached 4.63 pages/s against
4.68 for MLX-VLM; native uses Q4_K weights with F16 encoder mirrors while the
reference uses original FP16 weights and a different generation policy.
LightOn remains behind: opt-in residency runs reached 1.31/0.44 pages/s for
0.8B/4B against 2.72/0.76 for vLLM Metal. Successive runs under uncontrolled
machine load are exploratory comparisons. The earlier projection-only
ablations did not establish page-throughput gains.

`TERMITE_METAL_ENABLE_LIGHTONOCR3_WEIGHT_RESIDENCY=1`, set before preparing the
model, wires already-admitted dense weights without copying them. It is off
by default, bounded to 12 GiB and 32 residency sets, and releases cleared slots
and runtime allocations. The benchmark exposes `--weight-residency`. Existing
memory admission still applies; qualify this option under your workload's
memory pressure before selecting it.

Additional rollback switches are
`TERMITE_METAL_DISABLE_LIGHTONOCR3_DOWN_SPLIT=1`,
`TERMITE_METAL_DISABLE_LIGHTONOCR3_FOUR_ROW_TILE=1`,
`TERMITE_METAL_DISABLE_QWEN35_PREFILL_CONV_VEC4=1`, and
`TERMITE_METAL_DISABLE_F16_ENCODER_MPP=1`.
Full measurements, negative ablations, precision differences, source/binary
hashes and 73 passing focused GPU tests are retained in
`zig/pkg/inference/scripts/lightonocr3/results/projection_parity_m4_max/README.md`.

### Recurrent prefill and cohort kernel follow-up

The next pass fuses small-cohort gate/up plus SiLU × up, distributes recurrent
prefill across four value columns per SIMD group, and retains wide normalization
inputs in registers across the F32 reduction. It also uses narrower split-K tiles
for qualified four-row projections and a more parallel single-token 0.8B down
projection. Existing frame-owned scratch is reused. Projection activations,
accumulation, outputs and recurrent state retain F32 precision.

A new regression test invokes the Zig batch gate/up wrapper: an earlier guard
rejected small batches despite successful direct C kernel tests. The final
runtime removes that guard and delegates qualification to the C selector.

A stronger paired benchmark alternates native and MLX in one process, reverses
trial order, checks every output and records every sample. In the final resident
sweep, 38 of 43 cases are within 20% of MLX or faster; five remain 22–34% slower.
The 25-case cold-cache sweep puts every case within 20%. Recurrent prefill is
1.6–1.8× faster than MLX on the two tested head counts; F32 normalization is at
parity or faster. Native projection/recurrent tensors remain F32 while MLX uses
BF16 storage/output, so this is not fully precision-matched operator parity.
These paired results supersede the earlier separate-process projection summary
as the stronger evidence; cache effects materially change small-matrix results.

On the same shared machine, final 16-page reader runs measured 1.079/0.339
pages/s for native LightOn 0.8B/4B versus refreshed vLLM results of 2.553/0.647.
New-feature rollbacks measured 1.001/0.337: 0.8B improved in this run, while 4B
was effectively tied. Florence measured 3.546 versus 3.849 for refreshed MLX-VLM.
These successive runs remain sensitive to machine load. Whole-reader LightOn
parity is unfinished; cohorts averaged about 3.5 active pages out of eight as
short pages finished. Continuous refill and batched vision/prefill remain open.

Additional rollback switches are
`TERMITE_METAL_DISABLE_LIGHTONOCR3_BATCH_GATE_UP=1`,
`TERMITE_METAL_DISABLE_QWEN35_PREFILL_COLUMNS=1`,
`TERMITE_METAL_DISABLE_LIGHTONOCR3_PREFILL_NORM=1`,
`TERMITE_METAL_DISABLE_LIGHTONOCR3_SINGLE_DOWN_TILE=1`, and
`TERMITE_METAL_DISABLE_LIGHTONOCR3_FOUR_ROW_SPLIT=1`.
The concurrency benchmark exposes corresponding `--disable-*` switches.
Final reader measurements, numerical checks, build provenance, and the rejected
candidates are retained in
`zig/pkg/inference/scripts/lightonocr3/results/kernel_saturation_m4_max/README.md`.
