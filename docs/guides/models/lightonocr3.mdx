---
title: LightOnOCR-3 document OCR
description: Run LightOnOCR-3-0.8B and 4B document parsers through Antfly's native inference runtime
---

LightOnOCR-3 is Antfly's recommended OCR model. The 0.8B and 4B checkpoints are Apache-2.0 document parsers based on Qwen3.5. Each
transcribes page images into Markdown, including HTML tables and LaTeX formulas.
Antfly uses the integrated safetensors checkpoint with the native Qwen vision
and hybrid-attention decoder paths.

## Install

```bash
antfly inference pull lightonai/LightOnOCR-3-0.8B:safetensors@36d8636925327c671bd8e479c517a004f7566bd9
```

The pull installs the upstream configuration, tokenizer, chat template, image
processor, and weights, plus a `model_manifest.json` declaring generation and
reading. Refer to the model as `lightonai/LightOnOCR-3-0.8B`; the short alias `lightonocr3-0.8b` also resolves.

Downloads made by older Antfly versions may lack `chat_template.jinja`. With an
updated Antfly, rerun the same pull command to fetch the missing sidecar while
reusing verified weights. Keep this file when sharing the model directory with
other runtimes: a bare image placeholder can produce silently empty pages.
Antfly's native reader uses its built-in equivalent of the trained image-only,
non-thinking prompt for both model sizes.

The larger model uses the same image-only prompt and `/read` API:

```bash
antfly inference pull lightonai/LightOnOCR-3-4B:safetensors@b71010f095dc3735de7ee6b9969bff8f8f50b39a
```

Refer to it as `lightonai/LightOnOCR-3-4B`. The 0.8B model needs about 1.7 GB for
weights and the 4B model about 9.1 GB, plus working memory. Both run on CPU,
Metal, and CUDA.

## Read a page

Send a rendered PDF page or other document image to the inference service:

```bash
curl http://localhost:8080/ai/v1/read \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "lightonai/LightOnOCR-3-0.8B",
    "images": [{"url": "data:image/png;base64,..."}],
    "max_tokens": 1024
  }'
```

Omit `prompt` or pass an empty string for transcription. This model is trained
with an image-only prompt; a generic instruction such as `Transcribe this page`
is rejected by `/read`. The alternative `"prompt": "grounding"` returns the
model's native labeled bounding-box markers, descriptions, and chart tables in
the result's `text`. These markers use coordinates normalized to 0–1000; they
are not converted into pixel-coordinate `regions`.

On Metal, and on CUDA with the LightOn batch profile, `/read` batches pages from
the same request and from concurrent requests on the GPU.

When `max_tokens` is omitted, both LightOnOCR-3 models default to 4096 output
tokens per page. HTTP and embedded reading use the same model-specific budget,
bounded by `resources.inference.request_limits.max_output_tokens_per_item`.

Set `max_tokens` explicitly to override the default, up to the `/read` ceiling
of 8192 and the selected model's and deployment's limits. Explicit values above
those limits are rejected rather than silently clamped. Truncated output is
still rejected. Use this endpoint for repeated page extraction so the reader
can reuse its prepared execution state.

For example, a dense page can request `"max_tokens": 8192`. The deployment
must also allow the output ceiling and provide enough memory for the request.
The larger budget increases its estimated work; work-unit accounting saturates
at `resources.inference.admission.max_work_units`, so a large request can occupy
the full configured capacity without bypassing competing requests. Concurrency,
memory, image, and input-token limits remain enforced.

The Go `docsaf/reading/antfly` adapter omits `max_tokens` by default, including
when falling back between models. Set `AntflyConfig.DefaultMaxTokens` for an
adapter default, or `reading.ReadOptions.MaxTokens` for a per-call override.
Positive per-call values take precedence over the adapter default.

For document ingestion, the same manual control is available as
`ocr.reader.max_tokens` alongside the reader provider and model.

Other OCR models retain their own prompt and output-budget rules: Qwen3-VL
uses its reader profile; encoder-decoder readers use their decoder metadata;
Moondream retains its caption budget; detection/recognition pipelines have no
generative output-token default.

## Run quantized models with llama.cpp

Run a recent `llama-server` on the GPU host. Use the GGUF decoder and matching
FP16 vision projector from the same model size. This example uses
[LightOnOCR-3-0.8B Q4_K_M](https://huggingface.co/richardyoung/LightOnOCR-3-0.8B-GGUF/tree/main).
The [0.8B](https://huggingface.co/richardyoung/LightOnOCR-3-0.8B-GGUF/tree/main)
and [4B](https://huggingface.co/richardyoung/LightOnOCR-3-4B-GGUF/tree/main)
repositories both supply Q4_K_M and Q8_0.

```sh
llama-server --model LightOnOCR-3-0.8B-Q4_K_M.gguf \
  --mmproj mmproj-LightOnOCR-3-0.8B-F16.gguf \
  --alias lighton-ocr --reasoning off -ngl 99 -c 8192 --parallel 1 \
  --host 127.0.0.1 --port 18090
```

Register it in Antfly's runtime configuration as an OpenAI-compatible reader.

```json
{
  "readers": {
    "lighton-quantized": {
      "provider": "openai",
      "base_url": "http://127.0.0.1:18090/v1",
      "model": "lighton-ocr",
      "prompt": "",
      "max_tokens": 4096
    }
  }
}
```

The empty prompt sends an image-only message for transcription. Set the prompt
to `grounding` for LightOnOCR's labeled layout output. Use
`readers/lighton-quantized` as the model in Antfly's `/ai/v1/read` request.
To serve the OCR API without a database process, use
`antfly inference run --config inference.json`. To build the focused
executable from source, run the following from `zig/`:

```sh
zig build inference-artifact -Doptimize=ReleaseFast -Dmetal=false
zig-out/bin/antfly-inference run --config inference.json
```

llama.cpp owns GPU execution in this deployment. The inference-only listener
defaults to `127.0.0.1:8090`. An explicit HTTP or HTTPS endpoint opts an OpenAI reader into hosted alias
registration. Existing readers that use the shared provider default can coexist
with these aliases. Endpoint precedence is `base_url`, then `url`, then
`api_url`. The listener validates the full image batch before sending one
completion per page. Set `hosted_parallelism` between 1 and 8 to limit the
number of simultaneous page completions within each request. It defaults to 1,
and results retain input order. The deployment output-token ceiling bounds the
reader default. Explicit request values above that ceiling are rejected.
These aliases accept `images` without artifact retention.
For a standalone database deployment, enable
[public inference](/docs/reference/inference-gateway#public-execution-policy)
to call that route.
For inline ingestion configuration, use the same reader object under `ocr.reader`.
If llama-server runs on a separate machine, set `base_url` to an endpoint
reachable from Antfly, such as a local SSH forwarded port.

### Extract entities from the transcription

Serve an instruction-tuned text GGUF in a second llama.cpp instance. Give its
`llama-server` an alias such as `invoice-extractor`, use a build that supports JSON Schema output,
and bind it on port 18091. Add an extractor alongside the reader in the
inference-only configuration.

```json
{
  "extractors": {
    "invoice-fields": {
      "method": "generated",
      "generator": {
        "provider": "openai",
        "url": "http://127.0.0.1:18091/v1",
        "model": "invoice-extractor",
        "max_tokens": 512,
        "temperature": 0
      },
      "output": "json_schema",
      "probabilities": "verdict_only",
      "schema": {"entities": ["invoice_number", "total"]}
    }
  }
}
```

Pass the text from the reader to `POST /ai/v1/extract`:

```json
{
  "model": "extractors/invoice-fields",
  "inputs": [{"id": "invoice-1", "content": "Invoice 12345. Total USD 42.00."}]
}
```

The generator endpoint can use `url` or `api_url`, including a secret reference.
The named extractor uses its configured entity and relation schema. Antfly
checks the returned structure and aligns entity text to spans in the input.
Hosted reading and extraction time out after two minutes or the caller's
shorter deadline. If a deployment sets an input-token limit, the upstream must
report prompt usage. An extractor call checks the entire upstream batch prompt,
including schema and instructions, against that limit. This accounting occurs
after the call because the upstream owns tokenization. The response omits usage
when any upstream call omits its counts. Hosted extraction limits each request
to 128 planned windows and caps aggregate upstream replies and serialized output
at 8 MiB each.
`GET /ai/v1/models` lists the reader under `readers` and the extractor under
`extractors`, with their accepted input modalities.

### Compare precision and working memory on Metal

Use the same llama.cpp build and source checkpoints for all precisions. The
benchmark expects `LightOnOCR-3-{size}-{precision}.gguf` and
`mmproj-LightOnOCR-3-{size}-{precision}.gguf` in the model directory. Convert the
original safetensors with llama.cpp's `convert_hf_to_gguf.py --outtype bf16
--no-nextn` for each BF16 decoder, and use `--mmproj --outtype q8_0` for each
quantized vision artifact. All baseline runs use the same F16 vision projector.
Use a tokenizer implementation compatible with the pinned tokenizer JSON if the
converter's Transformers version predates the checkpoint's tokenizer class.

From `zig/`, render the synthetic fixtures and run the sweep:

```sh
uv run --with pillow pkg/inference/scripts/lightonocr3/make_corpus.py \
  --output-dir .ocr-models/corpus --dense
python3 pkg/inference/scripts/lightonocr3/benchmark_llama_memory.py \
  --models-dir .ocr-models --cases .ocr-models/corpus/cases.json \
  --output .ocr-models/memory.json --parallel 1 4 --grounding
```

The sweep compares BF16, Q4, and Q8 decoders and tests smaller context and
prefill batches, a lower image-token cap, Q8 K/V, and a Q8 vision projector
independently. It reports warm idle, phase-sampled RSS and physical footprint,
whole-process peaks, completed pages per second, latency, and OCR checks.
Process startup is cold within each run. The system file cache is shared across
runs. The synthetic pages cover small print and tables, with a separate
grounding probe. They do not establish broad OCR accuracy. The harness retains
reports for incomplete profiles, including setup failures, and exits with a nonzero status when a page or
layout probe fails qualification. A qualifying page needs at most 5% character
error and all required text. The dense fixture also requires matching rows and
cells in an HTML or Markdown table. The receipt layout probe requires
at least three distinct, valid boxes. Memory qualification independently requires
RSS and physical footprint for each measured workload phase and both process
lifetime peaks.


## Read documents during ingestion

To OCR scanned PDF pages and images as they are indexed, name the model as the
`ocr.reader` of a `document_extraction` enrichment:

```json
{
  "type": "document_extraction",
  "config": {
    "ocr": {
      "reader": {"provider": "antfly", "model": "lightonai/LightOnOCR-3-0.8B"}
    }
  }
}
```

[Index PDFs and Scanned Documents](/docs/guides/index-documents) walks through the full table setup.

For dense pages, explicitly raise the per-page output budget:

```json
{
  "type": "document_extraction",
  "config": {
    "ocr": {
      "reader": {
        "provider": "antfly",
        "model": "lightonai/LightOnOCR-3-0.8B",
        "max_tokens": 8192
      }
    }
  }
}
```

The default remains 4096. A page warning containing `ReadOutputTruncated` means
the model reached its output budget before completing the page. Increase
`ocr.reader.max_tokens` within model and deployment limits, then reprocess the
artifact. If it already uses 8192, inspect the generated output for repetition
before raising other limits; additional memory cannot increase the `/read`
output ceiling. Incomplete OCR text is rejected.

Memory admission failures have two different remedies. `ResourceLimitExceeded`
means the page cannot fit its configured budget even when admitted alone. The
LightOn warning identifies the blocking budget, required bytes, and limit bytes,
with the applicable inference-server and standalone flags.
`ResourceTemporarilyUnavailable` means capacity is currently occupied or live
memory pressure prevents admission; the reader waits with backoff, bounded by
the request control and a 30-second stall timeout. Wide CUDA cohorts extend the
stall timeout only when cohort steps advance. The model manager emits at most
one admission denial diagnostic batch per second; `denied_count` includes
suppressed attempts.

## Image size

The runtime takes its pixel limits from the installed image processor, capped at
4096 merged vision tokens per image. Resize pages before submitting them when
optimizing latency; LightOn's own speed evaluation uses a 1540-pixel long side.

For PDF ingestion, `ocr.render.max_dimension` and `ocr.render.max_pixels` can
bound rendering memory. A 2048-pixel cap can help large pages fit, but can also
remove small print, handwriting strokes, and table detail. Compare transcription
quality before adopting it for a corpus. Larger memory budgets likewise need
headroom for concurrent requests and other server work.

Execution details, GPU tuning switches, and measured throughput are in the
[LightOnOCR-3 runtime notes](../../design/inference/lightonocr3-runtime.md). Published
quality numbers are in [LightOn's evaluation](https://huggingface.co/blog/lightonai/lightonocr-3).
